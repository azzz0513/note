# 上下文压缩与Token管理
Claude是无状态的，每一轮请求，都得把完整的对话历史发过去，Agent读的每一个文件、执行的每一条命令、产生的每一段输出，全部堆在消息列表里，Token数量随着对话轮次线性增长。

而Claude的上下文窗口有上限，200K tokens听起来很多，但在Agent场景下真的不够用，一个1000行的源文件大约15000tokens，读10个文件就是15万，再加上命令输出、搜索结果、AI的回复，轻松逼近200K，一旦撞到上限，API直接报错，Agent就瘫了。

上下文管理要解决的核心问题就一个：在有限的Token预算内，保留最有价值的信息，丢掉可以牺牲的信息。

工具结果是Token消耗的绝对大头，占了85%左右，而且很多工具结果的保质期很短。比如：Agent在第3轮读了`handler.go`，第5轮改了它，到了第10轮，第3轮读的那个旧版本还占着Token预算，但内容已经过时了。

既然工具结果占比最高又最容易过时，压缩自然要从他们下手，用户的对话反而是需要着重保留的核心

## 两层压缩

| 层级  | 手段                         | 信息损失 | API开销      | 触发条件         |
| --- | -------------------------- | ---- | ---------- | ------------ |
| 第1层 | 大结果存磁盘                     | 几乎为零 | 零          | 工具结果超阈值      |
| 第2层 | 摘要旧消息、保留近期原文（Auto-Compact） | 中    | 高（一次API调用） | token数逼近窗口上限 |
### 第1层：大结果存磁盘
所有处理都发生在工具结果进入对话历史之前，超限的内容在入口处就被换成预览，消息写进历史的那一刻就是最终形态，之后任何一轮都不再改动。

#### 单个工具结果超限
当一个工具的执行结果超过50000个字符（大约12500 tokens），系统不会把完整内容塞进对话历史，而是做两件事：
- 把完整结果写到磁盘的一个文件里
- 然后在对话历史里只放一个预览加文件路径

模型看到的大概是这样的：
![[Pasted image 20260725171402.png]]
为什么这一层几乎零损失？因为完整结果还在磁盘上，如果模型后面需要看完整内容，用ReadFile读那个文件就行，而且这一层没有任何额外API开销，就是一次本地文件写入。

不过`用ReadFile读回`有一个闭环要处理：读回的内容和原始结果一样大，如果照常溢写，模型拿到的又是一个预览加路径，再读回又被溢写，永远看不到全文，所以溢写文件的读回结果会被直接放行，不做溢写。

实际使用中模型也很少需要一口气读回全文，预览里已经能看出结果的结构，用ReadFile的offset和limit参数按需读一段就够了。

#### 每条消息的聚合限制
光管单个结果还不够，想象一下，一轮循环里Agent并行调了10个工具，每个结果都是40K字符，单个都没超50K单条阈值，但合起来就是400K。

所以还需要一个每条消息的聚合限制：一轮并行调用的所有结果会进入同一条user消息，写入历史前先合计总量，超过200000字符就把最大的那些存盘，直到总量降到预算以内。

比如五个工具返回42K、38K、45K、40K、44K，合计209K超了9K，挑最大的45K那条存盘替换成预览，其余四条保留原文，这条消息就定型写入历史。
![[Pasted image 20260725212103.png]]

#### 写入即终态与Prompt Cache
替换之后对话里存的就是preview，不再保留原文，原始内容只在磁盘存盘文件里，需要的时候模型用ReadFile读回来。

这种做法对Prompt Cache天然友好，Prompt Cache的工作原理是如果这一轮请求的消息列表前缀和上一轮完全一样（逐字节一致），API可以跳过前缀部分的处理只处理新增的消息，而历史里的每条消息从写入起就不再变化，每一轮请求里老消息都和上一轮逐字节相同，前缀稳定不需要任何机制来专门维护，它是写入即终态的副产品。

这也是上下文管理里一个容易被忽视的设计约束：不仅要考虑保留什么信息，还要考虑改动对话前缀的代价，如果每轮都重新评估、重新改写历史里的老消息，prompt cache命中率会直接归零，每轮请求都在为重复处理前缀买单。

### 第2层：摘要旧消息、保留近期原文（Auto-Compact）
当第一层不够用了，上下文仍然接近爆炸，就要：调用LLM自己来生成一份对话摘要，把较早的那些消息换成摘要，同时把近期原文留下来。

这是代价最高的一层，需要额外调一次API，花钱，而且被摘要掉的部分不可能保留所有细节，信息丢失不可避免，但它也是压缩效果最强的一层，能把十几万Token的早期对话压缩到几千Token，再配上保留的近期原文，模型既不会撑爆窗口，又能看清最近发生了什么。

#### 什么时候触发
以200K Token的上下文窗口为例，阈值是这么算的：
![[Pasted image 20260725213130.png]]
为什么要留13000的安全余量？
自动压缩的检查点是每轮循环开始时，调API之前，检查通过后，模型回复，执行工具，产生新的tool result，这些新增内容在下一次检查之前是没有被覆盖到的，而且模型可以在一次回复中发起多个并行工具调用，一轮下来可能同时新增好几个tool result，13000的buffer就是给这个两次检查之间的盲区留的余量。

13K是一个经验值，不是精确推导出来的，可以自己根据实际场景设一个合适的数，它也不需要精确，因为即使超了也不会崩，后面`紧急压缩`会兜底：API返回prompt_too_long时，Agent自动触发一次压缩再重试，不会直接瘫掉。

#### 为什么是固定值而不是百分比
因为buffer保护的是`单轮波动`，不是`总量`，每一轮Agent循环新的token量是相对固定的：读一个文件大约15K token，跑一条命令几百到几千token，不管你的窗口是200K还是1M，一个ReadFile都是那么大，buffer要防的风险是`下一轮突然多了一个大工具结果`，这个风险的大小取决于单次工具结果有多大，跟总窗口无关。

#### 为什么预留20K给摘要输出
这个20000是被两个约束从两头夹出来的。

下限来自摘要本身的需求，摘要有9个结构化部分，加上`<analysis>`草稿块，一次复杂会话的摘要输出大约15000到18000 tokens，设成15K就有被截断的风险。

上限来自有效窗口的压力，预留越大，有效窗口越小，压缩就触发得越频繁，如果预留50K，有效窗口缩到150K，自动压缩在137K就触发了，但摘要根本用不了50K。

#### 摘要Prompt的设计
摘要质量直接决定了压缩后Agent的表现。一个好的摘要Prompt要求LLM生成一份结构化摘要，明确指定9个部分：
![[Pasted image 20260725214604.png]]
第6条：**用户说过的话尽量原文保留**。因为用户的原始表述包含意图、偏好、预期。

原文才能准确传达意图，当然，如果对话很长，用户消息很多，LLM不可能在有限的摘要空间内塞进所有原文，这更多是一个优先级指引：告诉LLM用户消息优先保留原文而不是随意改写，空间不够时自然会取舍。

#### 两阶段生成：先打草稿再写正文
Prompt要求LLM先产出一个`<analysis>`草稿块来梳理思路然后产出正式的`<summary>`块，最终只保留summary，analysis被丢弃。

这能显著提升摘要质量，分析阶段让LLM先把对话中发生了什么梳理一遍，然后在此基础上写摘要会更全面、更精确，但analysis本身作为中间产物没有保留价值，占了空间反而浪费，所以生成完就扔掉。

#### 禁止工具调用
Prompt 还需要一段强硬的开头，明确禁止模型调用任何工具、只输出纯文本，为什么需要这条禁令？因为摘要 API 调用复用了原对话的消息上下文，工具定义会随消息一起传入这次调用，模型仍然「看得到」可用工具，如果不明确禁止，LLM 可能「好心」地试图调一个工具来帮你，结果浪费了这次调用。

MewCode 调摘要 API 时会保留`tools`参数，这样做是为了让压缩请求的前缀和正常请求完全一致，命中 Prompt Cache，为了防止模型在压缩时调用工具，除了 prompt 里两头堵的禁令外，压缩代码只读取文本输出，工具调用事件直接忽略。

#### 压缩后恢复
第 2 层并不是把整段对话都换成摘要，它的做法是把较早的消息摘要掉，同时保留近期原文：从尾部按 token 往回数，大约最近 1 万 token 或者至少 5 条消息留作原文，且不会从中间切断 tool_use 和 tool_result 的配对，这部分近期原文一字不改地留在对话里，模型最近做了什么、刚刚说了什么，看的都是原话而不是摘要。

在保留的近期原文之外，还有一些被摘要掉的关键上下文需要重新附加回来：
- 最近访问的文件：最多恢复5个，每个最多5000Token。Agent压缩后仍然记得最近度过的文件
- 技能定义：如果之前使用过Skill，重新注入定义，总预算25000Token

会话记录路径的设计防止模型「编造」摘要里没有提到的细节：摘要里写「修复了 handler.py」，模型如果想引用具体代码，就得去读会话记录或者重新 ReadFile，而不是根据模糊描述脑补一段不存在的代码。

### 熔断机制
如果全量摘要因为网络问题、API错误或prompt-too-long等原因连续失败3次，系统停止自动触发。

#### 强制压缩线：熔断之后的保底
熔断虽然防止了死循环，但带来了一个新问题：自动压缩停了，token还在涨，上下文会越来越逼近窗口上限。

为了应对这种情况，系统在 effectiveWindow - 3,000 的位置（以 200K 窗口为例就是 177K）设了一条强制压缩线，每轮循环检查 token 用量时，如果已经越过了 177K，不管熔断状态如何直接执行一次 ForceCompact，这条检查在熔断判断之前，优先级最高。

#### 紧急压缩：撞墙后的自救
上面讲的都是调 API 之前的预防措施，但还有一条路径需要处理：预防措施全都过了，正常的对话请求发出去后，API 返回 prompt_too_long 错误。

​这说明所有阈值都没挡住，可能是 token 估算偏差太大，也可能是某一轮工具结果异常巨大，两次检查之间直接跳过了阈值，不管什么原因，结果就是上下文已经超了 API 的硬限制，请求被拒绝了。​

如果没有任何处理，Agent 就直接报错停工了，用户只能手动 /compact 然后重试，体验很差，​MewCode 的做法是在 Agent Loop 里捕获这个错误，立刻触发一次 ForceCompact，压缩完成后用新的消息列表重试原来的请求，相当于「撞墙了，赶紧压缩，然后再试一次」，如果压缩后仍然超限，就按正常错误流程处理，不再无限重试。

​到这里整套防线就完整了：token 用量到 167K 触发自动压缩，连续失败 3 次后熔断停止重试，涨到 177K 时强制压缩兜底，这三道都是调 API 之前的预防，如果还是漏过去了、请求被拒，紧急压缩在调 API 之后补救，压缩完成重试原请求，Agent 不至于因为一次估算偏差就彻底瘫痪。

### 手动`/compact`
除了自动压缩，用户随时可以输入`/compact`手动触发。两个典型场景：
- 预防性压缩：你知道接下来要读一大堆文件，提前压缩腾出空间
- 话题切换：前面的对话在调bug A，现在要处理bug B。手动压缩清理掉bug A的细节，减少噪声

# 给Agent跑一次真实测评
## 评测在测什么
Agent 有随机性，同一个任务跑两次，它可能走完全不同的路径、调不同的工具、写出不同的代码，靠手动试几个 case 拍脑袋说明不了问题。​​

评测干的事就一件：拿一批真实任务喂给它，用自动化的测试判它能不能做完，让「好不好用」变成能量化、能复盘的结果。

​​我们用 SWE-bench-Live 这个现成的题库，它是微软维护的，每月从 GitHub 上收录最新的真实 issue，给你 bug 存在时的代码版本和 issue 描述，让 Agent 自己定位自己修，修完在 Docker 容器里跑原项目的测试来判过没过。​​

选它是因为题够新、够真实，而且官方还配了一套现成的 harness，省得自己造。​​

harness 这个词后面会反复出现，它指的就是官方那套判分工具，负责起 Docker 容器、把你的补丁打上去、跑测试、出结果，这一章里说的判分全是它在干活。

## 环境准备
评测要在 Docker 容器里重建每个仓库的运行环境，所以系统得是 Linux、Mac 或者 WSL2，装好 Docker，Python 3.10 以上，内存 16GB 起步。​​

开跑前先算笔账，好决定自己要跑几道，每道题对应一个预构建好的 Docker 镜像，一个镜像一两个 G，跑十道题准备二十来个 G 的磁盘也就够了，不用真按上百 G 去留。

​​时间上，让 Agent 修一道题大概几分钟到二十分钟，看它折腾的程度，判分那边首轮要拉镜像，一道题十来分钟，镜像缓存下来之后重复跑就是一分钟的事。​​

这些成本基本是线性的，每多一道题就多一个镜像加一轮跑，所以跑几道完全由你自己定，机器紧就少跑两道，跑通一道也照样能复盘。​​

网络在国内会卡两处，Docker 镜像托管在 Docker Hub 上，数据集在 HuggingFace 上，两边都得先能连上，代理或者镜像加速提前配好，别等跑到一半才发现拉不动。

## 把评测交给Claude Code
我自己跑这套评测，基本不手敲那十来条命令，我把整条流水线整包交给 Claude Code，我只当甲方，看它把结果端上来。​​

先把角色说清楚，Claude Code 是执行评测的操作员，被评测的是我自己的 Agent，任务不是 Claude Code 在解，是它替我把我的 Agent 架到评测台上跑一遍。​​

把下面这段提示词里的占位符换成你自己的，粘给 Claude Code 就行，踩过的坑我都写进去了，尤其是封 git 历史那条，不封的话你的 Agent 会顺着 git log 把正确答案抄出来，测出来的分是假的：
```
你是我的评测执行助手。我要用 SWE-bench-Live 评测我自己写的 MewCode。 它非交互跑一道题的命令是（Java、Python 版就换成你那版的启动命令）： 

mewcode -p "<把任务描述放这里>" 

请按下面的步骤端到端把评测跑完，每做完一步打印一句结果再往下走： 

1. 装 harness：git clone --recurse-submodules https://github.com/microsoft/SWE-bench-Live， 建 venv，然后 pip install -e . 安装（末尾那个点是当前目录，别漏）。 子模块漏了后面会报 launch.core 找不到。 

2. 拉数据：export HF_ENDPOINT=https://hf-mirror.com，用 datasets 加载 SWE-bench-Live/MultiLang，split 按你想跑的题目语言选（比如 split="go"）， 按 created_at 倒序挑最新的 {N} 道， 把每道的 instance_id、repo、base_commit、problem_statement、FAIL_TO_PASS 存成一个 json 备用。problem_statement 里明说要 Postgres、MySQL 或别的外部服务的题先跳过。 

3. 对每道题，准备一个封了历史的工作副本：完整 clone 仓库后，用 git archive <base_commit> | tar -x 把那一刻的文件树抽到一个新目录，再 git init 重新提一个 commit。这样副本里只有一个提交，我的 Agent 顺着 git log 也翻不到 未来的正确代码。这一步很关键，不封历史测出来的分是假的。 

4. 在这个副本里，把 problem_statement 作为任务，用上面的命令喂给我的 Agent， 让它非交互跑到自然结束，中途不要插手。任务描述先写进文件再读进来，别直接拼在 命令行里，issue 正文里的引号和美元符号会被 shell 吃掉。跑的时候必须把完整过程 存下来，这份记录后面复盘全靠它： mewcode -p "$(cat task.txt)" --output-format stream-json > logs/<instance_id>.jsonl 2>&1 

5. 收补丁：git add -A 之后用 git diff 导出改动，但排除两类东西，一是我的 Agent 自己写进仓库的运行时目录（如 .mewcode/、.claude/），二是所有测试文件（*_test.go、 test_*.py 之类），因为判分时 harness 会注入它自己的测试，补丁碰了测试文件会冲突。 把每道题的补丁汇总成 predictions.json：{"<instance_id>": {"model_patch": "<diff 文本>"}}。 
   
6. 先用 gold 补丁校验环境： python -m evaluation.evaluation --dataset SWE-bench-Live/MultiLang --split {你的语言} --platform linux --instance_ids <所有题> --patch_dir gold --output_dir logs/gold --workers 1 --overwrite 1 读每道题的 logs/gold/<id>/report.json，resolved 是 false 的说明环境失效， 从题库里剔掉，别拿它算我 Agent 的分。 
   
7. 拿我的 predictions 跑正式评测：同样的命令，--patch_dir 换成 predictions.json， --output_dir 换成 logs/eval。 
   
8. 汇总：读每道题的 logs/eval/<id>/report.json，统计 resolved 的题数算通过率。 对每道没过的题，看 FAIL_TO_PASS 和 PASS_TO_PASS 各自的 success 和 failure， 判断它是目标测试没过（没修对）还是碰坏了原有测试（回归）。 然后把第 4 步存下的 logs/<instance_id>.jsonl 也读一遍，report.json 里只有分数， Agent 为什么这么改、中途有没有改过主意、有没有哪次工具调用失败之后就放弃了某个 能力，这些只在那份记录里。摘出来跟分数放一起。 最后给我一张表：题号、resolved、失败原因、记录里发现的可疑点。 
   
开跑前先告诉我总共几道、大概多久、占多少磁盘，我确认了再开始。首轮拉 Docker 镜像很慢， 一道题可能十分钟起步，耐心等。
```

## 跑出来的分，多少算正常
第一次跑完，你大概率会看到一个很难看的数字，五道题解出一道，甚至一道都没解出来，先别急着怀疑自己写的东西是垃圾，这个分低本来就是正常的。​​

一个原因是题真的难，这个题库收的是最新的真实 issue，没进过任何模型的训练数据，模型只能老老实实读代码定位，没有背答案的余地。​​

另一个原因更值得你知道，我拿 Claude Code 接同一个模型、跑同一批题做过对照，五道题它解出两道，我的 MewCode 也解出两道，而且是同样的两道，栽也栽在同样的三道上，换到一道最新的题上，两边都没解出来。​​

所以你解不出来这件事，多半不是和成熟框架的差距，而是这个模型能力上限的差距。​​

给你一条参照线，我这组数是接 MiniMax-M3 跑出来的，五到十道最新的题里解出一到三道，属于正常范围。​​真正要警惕的不是分低，是另外两种情况，一种是 gold 校验都过不了，那是环境的锅不是你的锅；另一种是补丁压根是空的，那说明你的 Agent 中途就退出了，得回去看它为什么没跑完。

​​​gold 校验是正式评测前的一道体检，拿官方给的标准答案去跑那道题，连标准答案都跑不过，说明这道题的运行环境本身就是坏的，网络、依赖、镜像都可能出问题，这种题得先剔掉，别拿它算你 Agent 的分​​​

还有个数字最好提前有心理准备，我挑了十道题做 gold 校验，最后只有五道通过，剩下五道是环境本身失效，网络、依赖、镜像各有各的毛病。​​

所以你想手里最终留下五道有效的题，一开始就得多挑几道，别挑五道然后发现只剩两道能用。

## 看失败：翻记录，归个类
通过率只告诉你「挂了」，值钱的是搞清楚「为啥挂」，每道没过的题，翻一下 Agent 的对话记录，也就是跑的时候存下来的那份 jsonl，再对着它的 diff 看一遍，用一句话记下失败原因，归到下面几类里：​​

没定位到该改的文件，改错了地方；定位对了但修法不对，测试还是没过；修对了功能，却碰坏了别的测试；改动越滚越大，把简单问题搞复杂了；或者干脆超时、格式错、工具调用失败。​​

这里得提醒一句，别自己打开那份 jsonl 硬看，它是按事件流写的，Agent 说的话会被拆成一个字一个事件，满屏都是碎片，人眼根本读不下去。​​

让 Claude Code 帮你读，叫它把 Agent 的推理过程拼回完整的话、把报错的工具调用单独挑出来，你看它归纳完的结果就行，这一步不外包，大部分人翻两眼就放弃了。

​​那份记录里能翻到的东西比你想的多，Agent 说过的每一句话、它每次调工具传了什么参数、工具返回了什么、有没有报错、每一轮烧了多少 token、中途有没有触发过上下文压缩，全都按事件一条条记在里面。​​

所以让 Claude Code 读的时候可以直接点名要，比如把所有报错的工具调用单独挑出来，把它前后改过主意的地方标出来，或者问它这次跑有没有触发压缩、压缩是在第几轮发生的。

​​前面那两个例子就是这么翻出来的，Agent 自己否定自己那句藏在它说过的话里，子 Agent 被工具挡回去那次藏在工具返回的报错里，这两样东西通过率一个字都不会告诉你。​​

分完你会发现，失败不是「Agent 不行」一句话能概括的，有的是它压根没想对（这种得靠更强的模型或更好的提示词），有的是它想对了但没机会验证自己（这种给它一个能跑测试的环境、让它改完自己验一遍就能救回来）。

​​这个区分，就是评测真正给你的东西。​​

有个真实的例子能让这套归类活起来，我拿一道修并发消息丢失的 Go 题去测，issue 说的是用户连续发多条消息时只有第一条被处理，其余在会话锁定期间被悄悄丢掉。

​​Agent 一开始定位得很准，它自己在记录里都写下了「队列容量不足解释不了后面几条为什么丢」，还点出真正可疑的是「会话还在启动、处理器尚未就绪」那个判断分支，可几步之后它把这个结论推翻了，回到「就是队列太小」，最后只把容量常量从 5 改成 100 就收工，测试没过。

它为什么自己把自己劝退了，翻记录能看到原因，它读了仓库里现成的测试，那些测试锁定的正是当前这套有问题的行为，其中一条断言「某种状态下就该返回丢弃」，而我们给的任务里写了「不要改测试文件」。​​

这两条一夹，Agent 就不敢去动那个真正该改的判断分支，它觉得改下去会破坏现有测试，又不许改测试，于是退回到一个绝对安全、却根本没解决问题的改法，这既不是「模型太笨没想到」，它想到了，也不是「没机会验证」，是它卡在了任务约束和代码现状的冲突上，主动放弃了正确方向。​​

这种失败你盯着通过率一辈子都发现不了，只有翻进记录里才逮得到，而逮到之后能动的地方也很具体，比如把提示词里那句死板的约束改得松一点，别让它一见到测试就缩手。

## 改完再跑一遍
上一节把失败归了类，你手里就有了几条具体的、能动手改的东西，这一节讲改完之后怎么确认自己真的改对了，少了这一步，前面那些功夫只完成了一半。​​

复测的规矩只有一条，一次只动一个变量，还是那道题，还是那个模型，还是那份封了历史的工作副本，只把你改的那个地方换掉，然后重跑。

​​要是你既改了提示词又换了模型，跑出来变好了你也说不清是哪一下起的作用，下次碰到类似的问题照样没法复用这个经验。​​

看什么也得说清楚，很多人以为复测就是看通过率涨没涨，其实大多数时候你该盯的是记录里那个具体现象还在不在，原来那个报错还报不报，原来被放弃的能力回来没有，原来要来回折腾十几轮的地方现在几轮能收工。​​

这些是你能直接控制的东西，通过率不是。​​

我自己走过一遍这个循环，可以给你当参照，评测里我发现 Agent 的子 Agent 一次都没用起来，翻记录一看，是被自己工具的参数校验挡了回去，模型传了个不合法的参数组合，工具直接报错拒绝，它试了两次就彻底放弃了这个能力，退回主线程一个文件一个文件地搜。​​

我把那个参数从工具定义里去掉，同一道题、同样的条件重跑，报错消失了，子 Agent 一次就跑通，还产出了一份完整的探索报告，工具调用总数从三十几涨到六十几，它明显敢往深里查了。​​

但那道题最后还是没解出来。​​

这句你得记住，因为这是最容易让人半途放弃的一步，你修掉了一个真问题，分数却纹丝不动。​​

原因前面讲过，分数的上限是模型定的，你修的是框架这一层的毛病，它决定的是「模型的能力有没有被白白浪费掉」，不是「模型能不能想出这道题的答案」。

​​所以复测的时候别拿通过率当唯一的成绩单，那个具体现象消失了，就说明你这次改对了。

​​这个循环可以一直转下去，跑一批题，翻记录，挑出一条最碍事的，改掉，同条件复测，再跑下一批，转过三五轮，你对自己这个项目的了解会比任何一次性的分数都深。

## 怎么判断Agent到底行不行
跑出一个通过率之后，你八成想知道：这个分说明我的 Agent 好还是不好？先泼盆冷水，光盯着这个数字判断不出来，通过率的上限是模型定的，模型压根想不到的题，框架再精致也变不出答案来；但反过来不成立，框架自己出了毛病，是能把本来解得开的题也拖挂的。

​​所以这一个分里混着两件事，你得把它们拆开。

​​我实测过一次：拿 MewCode 和 Claude Code 接同一个模型，跑同一批真实 issue，通过率几乎一样，两个都解出同样的题、栽在同样的题上。

​​这不能说明两个框架一样好，只能说明那批题的难度正好卡在模型这一层，框架之间的差别还没机会显出来，要看出差别，得换个地方找。​​

所以判断你的 Agent，至少要分开看三件事，一是质量，也就是通过率，但一定要把模型钉死了再比，不然比的是模型不是框架。

​​二是效率，同一个模型下，跑完一道题烧了多少 token、花了多长时间、来回了多少轮，上下文管理做得好的框架，每一轮喂给模型的东西更精简，更少的轮次就能收工，token 和钱都省。​​

三是你框架自己的毛病，工具调用报错、参数校验把模型挡在门外、超时、某个能力压根用不起来，这类问题通过率一个字都不会告诉你，只能翻记录才看得见，可它们恰恰是你唯一能直接动手改掉的部分。​​

第三件事我自己就撞到过，翻一道失败题的记录时我发现，Agent 本来想派个子 Agent 去并行搜代码，结果连着两次调用都被自己的工具挡了回来，报的是参数组合不合法，它试了两次就放弃了子 Agent，改回主线程一个文件一个文件地翻，又慢又费 token。​​

这跟模型强不强没有半点关系，纯粹是工具的参数面留了个能踩空的洞，模型没仔细读参数说明就掉了进去。​​

这种问题不跑评测、不翻记录，你一辈子都发现不了，可一旦找到，改起来就是几行的事。​​

然后我有次实测，质量上两边打平，效率上我比的是轮次和耗时，同一道题 MewCode 二十几轮就收工，Claude Code 跑了三十多轮，耗时也是 Claude Code 那边更长一些（面试自己说合理数值即可）

## 这个对比怎么跑
把 Claude Code 拉来当对照，关键只有一条，除了 Agent 本身，其他所有条件都要一模一样，同一个模型、同一段任务描述、同一个 base commit、同一份封了历史的工作副本，少钉死一样，测出来的差距就说不清是谁造成的。​​

Claude Code 接第三方模型走的是环境变量，把它指到你给 MewCode 配的那个模型上，再用非交互模式跑：
```Bash
export ANTHROPIC_BASE_URL="<你的模型服务地址>"
​export ANTHROPIC_AUTH_TOKEN="<你的 key>"​
export ANTHROPIC_MODEL="<和 MewCode 用的同一个模型>"​
claude -p "$(cat task.txt)" --output-format json --dangerously-skip-permissions
```
任务描述从文件读进来，别直接写在命令行里，issue 正文里的引号、反引号、美元符号会被 shell 吃掉，`--output-format json` 会把轮数、token、耗时都吐在结果里，正好是你要记的效率数据。

​​Claude Code 也一样会往仓库里写自己的运行目录，叫 .claude，排除清单里记得一起加上。

​​这里有个坑我自己撞过，头一回跑对比时我没封 git 历史，结果 Claude Code 顺着 git log 翻到了后来那个修复提交，把正确答案原样抄了下来，测出来它「解出了」而 MewCode 没有，封上历史重跑，两边都没解出来。​​

所以在对比场景里封历史比单跑评测更要紧，不封的话，谁更会翻 git log 会被你误当成谁的能力更强。

​​跑完你手里会有两组数，一组是各自解出几道，一组是每道题各自烧了多少 token、跑了多久、来回了多少轮。

​​第一组大概率差不太多，甚至会出现两边栽在同一道题上，这不是白跑，它恰好说明这道题卡在模型的天花板上，跟框架没关系。​​

真正要盯的是第二组，同样都解出来的题，谁的轮次更少、喂给模型的上下文更精简，那才是框架自己的本事。​​把

这个想明白，你对自己项目的判断就从「我得了多少分」升级成了「我的框架在哪个维度追平了、在哪个维度还差、差在哪个模块」，这个认知本身，比那个分数值钱得多。

## 面试怎么讲
简历上写了「搭建评测流水线」，面试官顺着问下来基本跑不出三个问题，你把这三个答顺了就够用了。

​​第一个问题，你这个测试具体怎么做的，你就说，我用的是 SWE-bench-Live，微软维护的题库，每月从 GitHub 收最新的真实 issue，好处是这些题基本没进过模型的训练数据。

​​我挑了五十来道最新的，把代码退回到出 bug 的那个版本，然后只把 issue 描述丢给它，问题出在哪、该怎么改，一个字都不提示，让它自己去找自己去修，中间我也不插手，一直跑到它自己收工。​​

它改完之后，我把它动过的代码导出成一个补丁，放到 Docker 容器里打上去，再跑这个项目自己原来的测试，issue 对应的那几个测试必须全过，本来就能跑通的测试一个都不能被弄坏，两边都满足才算这道题过了。​​

这里有两个细节值得主动说，一个是正式跑之前，我先拿官方的参考补丁把所有题过了一遍，连正确答案都跑不过的题，说明环境本身就是坏的，我把这些剔掉了，五十来道最后只剩二十几道有效的。​​

另一个是工作副本我把 git 历史封掉了，因为答案就躺在后面的提交里，不封的话 Agent 顺着 git log 就能把正确代码抄出来，测出来的分是假的。​​

第二个问题，效果怎么样，二十几道有效的题解出七八道，三成左右。​​

这个数单看没什么意义，所以我又做了个对照，把模型钉死，让我的 Agent 和 Claude Code 接同一个模型跑同一批题，结果通过率几乎一样，解出的是同样那几道，栽的也是同样那几道。​​

这说明通过率的上限主要由模型决定，光看这个分判断不出框架的好坏。​​

第三个问题，效率和 token 消耗怎么样，这三样我都比过，同一道题我这边二十几轮就收工，Claude Code 要三十多轮，耗时也是它更长，五十来道整批跑下来，token 总量我这边少两成左右。​​

真正的差距在上下文管理的质量，任务一长触发压缩，我这边容易把早先的关键约束弄丢，结果改对一处又碰坏另一处，这个问题就是我在评测里发现之后专门去修的。

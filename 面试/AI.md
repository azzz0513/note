## AI-Coding笔试
### 题面里的规则，原样搬，不要自己概括
这是第一位的，也是最反直觉的。

大多数人读完需求文档的第一反应是「我懂了」，然后用自己的话跟 AI 复述一遍。问题就出在这一步：**你一概括就会变形，而判题是按原文那套规则走的。**

比如文档写「优惠叠加后金额若为负，按 0 计」，你概括成「金额不能是负数」——听起来一样，实际差着一个「叠加之后才判断」的时机。这种偏差你自己发现不了，因为你概括的时候是真的觉得意思没变。

正确做法是**逐条搬运**。真实的需求文档一般分几块：业务背景、功能要求、技术限制、验收标准、交付物、加分项。按这几块分别把原句拎出来，顺序本身就是结构，不用你重新组织。

写第一段指令的时候，规则那一节直接是文档里的原话，一个字都不改。

### 第一段指令决定后面所有轮次
上来一句「帮我实现一下这个系统」，等于把所有判断权都交给模型，然后用剩下的全部时间给它擦屁股。

第一段指令的骨架长这样：
![[Pasted image 20260813214506.png]]
```text
你是一个后端工程师，实现文档里的系统。  
  
【环境与运行方式】  
（把题面里关于语言、框架、入口文件、启动命令、端口、依赖、  
  有没有网络的规定，原样抄过来）  
（题面没提到的，先问我，不要自己假定）  
  
【业务规则】  
（把文档里的规则原样搬过来，不要自己概括）  
  
【接口契约】  
（每个接口的路径、方法、请求体、响应体字段名、状态码，逐条写死）  
  
【边界要求】  
- 非法输入 400、资源不存在 404、鉴权失败 403  
- 金额保留两位 / 用整数分（按题目要求）  
- 失败的请求不能产生任何副作用  
- 同一请求重复提交不能重复生效  
  
【验收】  
写完之后你自己起服务，把每个接口打一遍，把结果贴给我。
```
指挥力不是按你说了几句算的，是按每句话携带了多少有效约束算的。说十句废话，不如把一句写扎实

### 「环境与运行方式」这一节，最容易被跳过
上面那个骨架里，第一节是漏得最多的。

各家对入口文件叫什么、怎么启动、开哪个端口、能不能装第三方包、有没有网络，规定差别很大。而模型不知道这些，它会按自己训练时最常见的习惯来——只要跟题面不一致，第一版必然跑不起来，你就白白烧掉一整轮。

**把题面里写的原样抄进去，一句话省一轮返工。** 题面没写的，问，不要让它自己假定。

### 响应体字段名，逐字写死
这条单独拎出来，因为它是最冤的丢分方式。

业务逻辑你可能全做对了，状态机也对，金额算得也对——但如果没告诉模型返回的 JSON 长什么样，它会按自己的习惯编一套字段名出来。判题程序是按字段名取值的，名字对不上，取到空，这一条就是 0 分。

所以接口契约那一节，**路径、方法、请求体字段、响应体字段、状态码，五样逐条写死**。这是整篇里投入产出比最高的一段字。

### 动手之前，先排一次优先级
很多真题的需求量是**故意写不完的**——全局时钟、多段审批流水线、追溯调整，堆到明显超出考试时长。

这不是题目出难了，这是考点本身：**在时间不够的前提下，你怎么排优先级。**

所以读完文档别急着写指令，先花两分钟列一份功能清单，标出哪些是主干（不做整个系统跑不起来）、哪些是叶子（少一个只丢一个功能的分）。然后按主干优先的顺序推进。

最忌讳的是从文档第一页开始顺着往下做——顺序做完时间到了，主干还缺一半。

### 提交之前，让 AI 造一批用例来打你自己的代码
这是我认为整场笔试里性价比最高的一个动作，也是最容易被跳过的一个。

道理很简单：**隐藏用例你猜不到，但文档里写了的规则，AI 逐条对照穷举，比你在考场那个状态下临场回忆要全得多。** 等于提交之前你自己先模拟了一轮判题。
![[Pasted image 20260813214828.png]]
第一段，让它造用例：
```text
读一遍需求文档，针对我当前的实现写一批测试用例。  
重点覆盖正常流程之外的情况：  
- 非法输入（类型不对、缺字段、超范围、空值）  
- 边界值（0、负数、最大值、空集合、单元素）  
- 状态相关（不该允许的流转、终态还想改、重复提交同一请求）  
- 数值精度（小数、取整方向、金额）  
- 文档里写了但我可能没实现的规则，逐条对照列出来  
  
把用例写成可以直接运行的文件，先不要改我的业务代码。
```
最后那句 **「先不要改我的业务代码」不能省**。不加的话它会一边造用例一边顺手改实现，你就分不清是代码本来就对、还是它刚刚偷偷改对的了。

第二段，把挂掉的贴回去：
```text
以下用例没通过：【贴完整的失败输出】  
逐条告诉我每条为什么挂，然后挑改动最小的方式修，修完把这批用例重跑一遍。  
已经通过的那些用例涉及的逻辑，不要动。
```
「已经通过的不要动」这句同样必需。不加，模型很容易修好一条、弄坏两条，你还得再花一轮把它绕回来。

跑完大概率会挂几条——这是好事，说明你提前捞回来了几分。这个循环走两三轮，分数往上抬的幅度，通常比你再多做一个功能要大。

如果考试环境没有运行条件，把这招换成「读代码自查」：让它逐函数过一遍代码、输出边界漏洞，你逐条确认。

### 报错先诊断，别让它直接改
第一次生成的代码跑不起来，是常态，不是你的问题。别在「是不是我哪里搞错了」上耗心态，把它当成流程里必然的一步。

但贴报错的方式有讲究——**别让它上来就改**：
```text
这段报错贴给你：【完整错误信息】  
  
先别动代码。跟我说三件事：  
1. 它到底为什么会错  
2. 你打算动哪个文件的哪一段  
3. 这个改动会不会碰到已经跑通的部分  
  
我确认之后你再改。
```
关键是最后那句「我确认之后你再改」。少了它，模型很容易为一个小错把整个文件重写一遍，或者一路改下去把本来好的地方带坏——等你发现，已经不知道该退回哪一步了。

另外，**报错要贴全，别只贴最后一行**。

### 同一个问题三轮没解决，换个新会话
这条最反直觉，但很管用。

同一段对话里反复修同一个错，前面所有失败的尝试都还留在上下文里。模型会被自己之前那些错误答案牵着走，越修越偏——你会明显感觉到它开始重复之前试过的方案。

**新开一个窗口，把报错重新贴一遍**，相当于把这些干扰全清掉，让它用干净的脑子重新看这个错。

判断时机就一条：同一个问题三轮没解决，换窗口。
![[Pasted image 20260813215105.png]]
同一张图里还有另一条：**只要提交之后分数是往下走的，立刻回到上一个好的状态。** 到了后期每一次改动都有风险，改坏的概率并不比改好低，而你没有「赌下一轮能翻回来」的时间预算。见好就收在这个考试里是能力，不是怂。

### 七个边界，题面往往不会逐条明写
就算你没时间造用例，下面这七条也要在第一段指令里点一遍。它们几乎每道题都会碰到，但文档常常只字未提——因为出题人默认一个靠谱的工程师不用教也会做。
![[Pasted image 20260813215147.png]]
- **非法输入**：字段缺了、类型不对、ID 不存在——应该返回错误，而不是直接崩
- **负数与归零**：金额算下来是负的，要不要 clamp 到 0
- **数值精度**：小数保留几位、往哪个方向取整；浮点直接相加会算出 `0.30000000000000004` 这种东西
- **空集合**：空列表、空订单，返回空结果还是报错
- **幂等**：同一个请求提交两次，不能产生两笔账
- **终态**：已完成、已取消之后还想改，应该被拒
- **失败不留痕**：被拒绝的那个请求，不能改动任何数据

还有一条配套的：**每写完一块就跑一次**，别攒到最后一起验。攒到最后是十个问题混在一起，你根本分不清是哪块坏的，而那时候时间已经不够你一个个拆了。

### 留四分之一的时间给验收，并且能把过程讲清楚
各家场次时长差别很大，有独立两小时的，也有整场机考里只建议占一小时的。**所以别背绝对时间表，记比例**：
![[Pasted image 20260813215329.png]]

|阶段|占比|20 分|40 分|60 分|90 分|
|---|---|---|---|---|---|
|读文档、列功能清单|10%|2|4|6|9|
|写第一段指令|15%|3|6|9|13|
|开发到跑通|40%|8|16|24|36|
|**造用例 + 打自己的代码**|**25%**|**5**|**10**|**15**|**22**|
|收尾提交|10%|2|4|6|9|
跟常见的时间安排比，最大的不同是**给「造用例 + 修」留了整整四分之一**。这段时间不产出任何新功能，只负责把已经写出来的东西从「大概能跑」变成「确实对」——而分数恰恰是按「确实对」给的。时间越紧越要保住这一段，宁可少做一个功能。

最后一条，容易被忽略：**你的完整对话过程是被看的。**

从面经反馈看，面试时面试官是能拿到你 AI Coding 作答记录的，可能会针对过程复盘：哪些设计是你想的、AI 帮了什么、为什么用这套结构、还有哪些没解决的问题。

练法很朴素——每做完一道题，花两分钟用三句话复述一遍：需求是什么、方案是什么、哪里出了问题怎么处理的。**讲不顺的那一步，就是你思路还糊着的地方。**

### 三类体型
#### HTTP 服务 / 业务系统（最主流）
**流出的真题**：蚂蚁 早餐店订单系统、美团 外卖订餐系统、京东 保险核心系统、百度 信贷核算引擎。

**给你什么**：一份业务需求文档——一组接口、一套状态机、一堆业务规则（金额怎么算、什么状态能转到什么状态、什么情况返回什么错误码）。

**你要交什么**：一个能跑起来的 HTTP 服务，判题程序直接打你的接口。

**考点集中在这几处**：
- **接口契约**：路径、方法、请求体、**响应体字段名**、状态码，一个都不能错。判题是按字段名取值的，名字对不上就是 0 分，哪怕你逻辑全对。
- **状态机**：合法流转要通，**非法流转要拒**。比如订单不能从「待确认」直接跳到「已支付」。
- **金额计算**：精度保留几位、往哪个方向取整、叠加优惠之后变成负数要不要归零。
- **错误码分层**：不存在返 404，业务拒绝返 409 或 400，鉴权失败返 403。很多人全用 400 糊过去，直接丢一批分。
- **幂等**：同一个请求提交两次，不能产生两笔账。
- **失败不留痕**：一个被拒绝的请求，不能改动任何数据。

**这一类的分水岭**：京东、百度那两道属于**需求多到写不完**的大工程题——全局时钟、多段审批流水线、追溯调整。**写不完是常态**，考的是你怎么排优先级：先把主干打通，还是先把某一块做深。

**怎么准备**：找一道真题，限时把接口契约那部分**一次性写进第一段指令**，练「把规则原样搬过去、不自己概括」的手感。这一类最忌讳边写边想。

#### 工具/引擎类
**流出的真题**：蚂蚁 AI 代码质量审查系统、蚂蚁 集群调度器、蚂蚁 视频剪辑引擎。

**给你什么**：一个命令行程序的规格，读 JSON 写 JSON，或者操作文件。

**这一类最鲜明的特征：朴素做法一定过不了。**
- 代码审查题，用正则硬凑能检出几条，但一碰到「干净文件不许误报」就崩——正确做法是走 AST。
- 调度器题，纯 FIFO 排队一定栽——正确做法是优先级 + 抢占，思路对标 K8s / Borg。
- 视频剪辑题，剪切随手加 `-c copy` 会出问题，变速忘了处理音轨也会挂。

**考点其实是「你懂不懂这个领域真实是怎么做的」。** AI 会给你一个能跑的朴素版本，但它不会主动告诉你这个版本在复杂场景下会死。

**怎么准备**：拿到这类题，**先花两分钟想「朴素做法会死在哪」**，然后把这个判断写进指令。比如「不要用正则匹配，用 AST 解析，保证干净文件零误报」。这句话值很多分。

#### 数据分析类
**流出的真题**：OPPO 网约车订单取消率归因分析。

**给你什么**：一批数据，加一个待验证的业务判断。比如「运营说新司机取消率高，想限制他们接单，你验证一下这个判断对不对」。

**这一类的坑不在代码，在结论。**

如果你直接算整体新老司机的取消率，会看到新司机确实更高，于是得出「运营是对的」——**这个结论是错的**。正确做法是**分层归因**：按城市、时段、订单类型、天气这些维度分别对比，会发现真正的原因藏在分布差异里，结论可能整个反过来。

代码写得再漂亮，结论方向错了就是零分。

**怎么准备**：数据分析岗、算法岗的同学要特别注意——**这一类跟后端题完全不是一个考法**。别套后端那套「三层解耦」，它的结构是「取数 → 分层归因 → 结论表达」。

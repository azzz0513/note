### 什么是黑盒测试
**Black Box testing** is based entirely on the program specification and aims to verify that the program meets the specified requirements. / **黑盒测试**完全基于程序规范，旨在验证程序是否满足指定要求。

Black-Box testing provides for **coverage of the specification**, but not full coverage of the implementation. That is, there may be code in the implementation that produces results not stated in the specification. / 黑盒测试提供了规范的覆盖，但没有实现的完全覆盖。也就是说，实现中可能存在产生规范中未说明结果的代码。

### 黑盒测试的原则（principle）
![[images/Pasted image 20260525201031.png]]
1. Test **against** the specification（**对照**规范进行测试）
2. Use test coverage criteria based on the specification（基于需求使用测试覆盖准则）
3. Develop test cases derived from the specification （开发根据规范导出的测试用例）
4. "Exercise" the specification （“行使”规范）

### Equivalence Partitioning 等价类划分
#### 什么是等价类划分？
An Equivalence Partition (EP) is **a range of values** for a parameter for which the specification states equivalent processing.
定义：等价划分 （EP） 是规范中规定的等效处理的**参数的值范围**。

例子：
```Go
// 判定是否为负
/*
可以划分为两个等价类，分别是
[math.MaxInt, -1]
[0, math.MinInt]
*/
func isNegative(x int) bool {
	return x < 0
}
```

#### 什么是等价类
![[images/Pasted image 20260525203037.png]]
等价类形成集合的分区。
Partition：相互不相交的子集的集合，其Union是整个集合

#### 等价类的分类
![[images/Pasted image 20260525203123.png]]
**Valid Equivalence Class（有效等价类）**
- 输入域中有意义的一组数据
- 用于验证系统功能和性能是否能被**准确地实施**
- 符合需求规格、程序应该正常接受的数据集合。

**Invalid Equivalence Class（无效等价类）**
- 输入域中无意义的一组数据
- 用于测试系统的**容错性**
- 不符合需求规格、程序应该拒绝的数据集合。

例如：
假设程序要求用户年龄要求：年龄必须在1~120之间
那么：1~120就是一个有效等价类，例如12、23、99都是有效等价类
同时，小于1、大于120、非数字等都属于无效等价类，例如0、123、abc都是无效等价类

![[images/Pasted image 20260525203334.png]]
- 根据定义/业务需求识别输入/输出
	- 例：表格/命令行输入/输出信息/计算等
- 根据被定义的输入/输出识别等价类
	- 范围识别

```Go
可以划分为三等价类，其中，一个有效等价类，两个无效等价类
有效等价类
[0, 100]
无效等价类
[math.MinInt, 0)
(100, math.MaxInt]
*/
func isValidScore(x int) bool {
	return x >= 0 && x <= 100
}
```
- 集合识别（有效集合、无效集合）

- 一个有效等价类（true）
- 一个无效等价类（false）

强制输入划分等价类：
- 一个有效等价类（valid）

等价类测试：从每一个等价类中使用一个元素

因为，现实系统中多个输入组合后，可能会产生新的问题

```

密码不能为空
```
单独测试：
- 用户名空
- 密码空
都没有问题
但是，用户名和密码同时位空
程序可能直接：
- 空指针

### 总结
- 等价类划分是最低限度的黑盒测试，每一个输入和输出的划分都至少会有一个值会被测试，使用最小数目的测试用例
- 这些测试很可能确保代码的基本数据处理方面是正确的，但它们并没有测试代码中做出的各种决策
- 这很重要，因为决策是代码中错误的常见来源。这些决策通常反映了输入分区的边界，或是需要特别处理的输入组合的识别

## Boundary Value Analysis（BVA边界值分析）
### 什么是边界值分析
- Boundary conditions are situations at the edge of the planned operational limits of the software. / 边界条件是软件计划操作极限边缘的情况
- Security flaws such as buffer overflow attacks exploit boundaries of array buffers. / 缓冲区溢出攻击等安全漏洞利用数组缓冲区的边界

### 如何选取边界值
1. Every parameter has a boundary value at the top and bottom of every equivalence partition. （每个参数在每个等价分区的顶部和底部都有一个边界值。 ）
2. For a contiguous data type, the successor to the value at the top of one partition must be the value at the bottom of the next. （对于连续数据类型，一个分区顶部值的后继值必须是下一个分区底部的值。 ）
3. The natural range of the parameter provides the ultimate maximum and minimum values.（参数的自然范围提供最终的最大值和最小值。）

### 常见的边界值
1. 循环：0、1、len(arr)-1、len(arr)
```Go
func search(nums []int, target int) int {
	left, right := 0, len(nums)-1
	for left <= right {
		mid := (left + right) / 2
		if nums[mid] == target {
			return mid
		} else if nums[mid] < target {
			left = mid + 1
		} else {
			right = mid - 1
		}
	}
	return -1
}
```
2. 数组：第一个元素`arr[0]`、最后一个元素`arr[len(arr)-1]`
3. 变量：最小值`math.MaxInt`和最大值`math.MinInt`
4. 链表：第一个节点和最后一个节点
5. 可接受字符（串）的最大长度和最小长度：用户名、密码
6. 表格/报告的：第一行、第一列、最后一行、最后一列

通常，软件测试设计几种类型的边界检查：数字、字符、位置、大小、速度、方向、尺寸、空间等

相应的，上述类型的边界值应为：最大/最小、前/后、上/下、最快/最慢、最高/最低、最短/最长、空/满等

### Combinational Testing（组合测试）
#### 什么是组合测试
There are a number of different techniques for identifying relevant combinations, such as _**Cause-Effect Graphs**_**,** _**Decision Tables**_ **and** _**Truth Tables**_. / 有许多不同的技术可以识别相关组合，例如因果图、决策表和真值表。

The analysis of combinations involves identifying all the different combinations of input **causes** to the software and their associated output **effects**. / 组合分析涉及识别软件输入原因的所有不同组合及其相关的输出效果。

The causes and effects are described as **logical statements (or predicates)**, based on the specification of the software. These expressions specify the conditions required for a particular variable to cause a particular effect. / 因果关系被描述为逻辑语句（或谓词），基于软件的规范。这些表达式指定了特定变量引起特定影响所需的条件。

#### 真值表
To test all the **different behaviors of the program**, a Truth Table is created. The inputs (“Causes”) and outputs (“Effects”) are specified as Boolean expressions (using predicate logic). / 为了测试程序的所有不同行为，创建了一个真值表。输入（“原因”）和输出（“影响”）被指定为布尔表达式（使用谓词逻辑）。

**Combinations of the causes** are the inputs that will generate a particular response from the program.
**Test Cases** are then constructed that will **cover all possible combinations of Cause and Effect**. For N independent causes, there will therefore be a total of **2^N** different combinations. The Truth Table specifies how the software should behave for each combination. / **原因的组合**是将从程序中产生特定响应的输入。然后构建测试用例，涵盖因果关系的所有可能组合。对于N个独立的原因，因此总共会有2^N个不同的组合。真值表指定了软件对每个组合的行为方式。

cause（原因）：就是输入条件
effect（结果）：就是系统行为/输出结果

例：`isNegative(x int) bool`
![[images/Pasted image 20260526183123.png]]

|                             | if x < 0 then return true | if not x < 0 then return false |
| --------------------------- | ------------------------- | ------------------------------ |
| Causes x < 0                | T                         | F                              |
| Effects<br><br>return value | T                         | F                              |

例2：`largest(x, y int) int`
```Go
func largest(x, y int) int {
	if x >= y {
		return x
	}
	return y
}
```

|                   | Rules |     |     |
| ----------------- | ----- | --- | --- |
| Causes            | 1     | 2   | 3   |
| x > y             | T     | F   | F   |
| x < y             | F     | T   | F   |
| Effects           |       |     |     |
| return value == x | T     | F   | T   |
| return value == y | F     | T   | T   |
 **Rule 1（第1列）：当 x 大于 y 时**
- **Causes (条件)**:
    - x > y 是 **T** (True)
    - x < y 是 **F** (False)
    - 举例：x = 5, y = 3
- **Effects (结果)**:
    - 因为 x >= y 成立，代码返回 x（返回 5）。
    - return value == x 是 **T** (True) -> 返回值确实等于 x。
    - return value == y 是 **F** (False) -> 返回值不等于 y。
**Rule 2（第2列）：当 x 小于 y 时**
- **Causes (条件)**:
    - x > y 是 **F** (False)
    - x < y 是 **T** (True)
    - 举例：x = 2, y = 8
- **Effects (结果)**:
    - 因为 x >= y 不成立，代码走 : 后面的逻辑，返回 y（返回 8）。
    - return value == x 是 **F** (False) -> 返回值不等于 x。
    - return value == y 是 **T** (True) -> 返回值确实等于 y。
**Rule 3（第3列）：当 x 等于 y 时（最巧妙的一列）**
- **Causes (条件)**:
    - x > y 是 **F** (False)
    - x < y 是 **F** (False)
    - 逻辑推理：如果 x 既不大于 y，也不小于 y，那么必然存在**隐藏条件：x == y**。
    - 举例：x = 4, y = 4
- **Effects (结果)**:
    - 代码执行 x >= y（4 >= 4），判断为**真**，所以代码实际执行的是**返回 x**（返回 4）。
    - return value == x 是 **T** (True) -> 返回值等于 4，也就是等于 x。
    - return value == y 也是 **T** (True) -> 因为 x 和 y 都是 4，所以返回值 4 **也等于 y**。
    - (这就是为什么 Rule 3 的两个 Effect 都是 T，因为虽然代码只返回了其中一个变量，但在数值上，它同时等于这两个变量。)

#### Don‘t Care Conditions
“Don’t care” conditions exist where the value of _**a cause has no impact on the effect**_. / “不在乎”条件存在，其中原因的价值对结果没有影响。

These “Don’t care” conditions are used to reduce the number of rules _**where the same output will be generated**_ irrespective of whether the **Cause is true or false**. / 这些“不关心”条件用于减少无论原因是真还是假都会生成相同输出的规则数量。

In the worst case, if there are no “Don’t care” conditions, N Causes will create 2^N Rules. / 在最坏的情况下，如果没有“不关心”的条件，N个原因将创建2^N个规则。

“Don’t care” conditions are represented by a **“*”** for the causes in a Truth Table. / “不关心”条件在真值表中用“*”表示原因。

例：
```Go
func condIsNegt(x int, flag bool) bool {
	if x < 0 && flag {
		return true
	}
	return false
}
```

| ------------ | ----- | --- | --- |
| Causes       | 1     | 2   | 3   |
| x < 0        | T     | F   | *   |
| falg         | T     | T   | F   |
| Effects      |       |     |     |
| return value | T     | F   | F   |
#### 优势和不足
The truth tables can sometime **be very large**. The solution is to identify subproblems and develop **separate tables** for each. / 真值表有时可能**非常大**。解决方案是识别子问题并为每个子问题开发**单独的表**。

**Very dependent on the quality of the specification** - more detail means more causes and effects, which takes more time to test; less detail means less causes and effects, but less effective testing / **非常依赖规范的质量**——细节越多意味着前因后果越多，需要花更多时间测试；细节越少意味着前因后果越少，但测试效果越差

Associate conditions with actions to perform / 将条件与要执行的操作相关联
Can associate many independent conditions with several actions in an elegant way / 可以优雅地将多个独立条件与多个动作关联起来

### Random Testing and Error Guessing
#### 随机测试
![[images/Pasted image 20260526204659.png]]
- Each Test Case is represented by **a set of (random) input values**, one for each parameter.
每个测试用例由一组（随机）输入值表示，每个参数一个。
- If the test is fully **automated**, then each Test Case is represented by a distribution of values for a particular parameter.
如果测试是完全自动化的，那么每个测试用例都由特定参数的值分布表示。
- This will normally include **the upper and lower limits, and the distribution** to be used between these limits to select a random value.
这通常包括上限和下限，以及在这些限制之间用于选择随机值的分布。
![[images/Pasted image 20260526204733.png]]

#### 错误推测
![[images/Pasted image 20260526204744.png]]
- 空值、空字符串、空数组、空列表、空的类引用
- 0 值
- 字符串的空格或者空字符串
- 负值

The tester selects values which are **likely to produce errors**. Each value is a Test Case. / 测试人员选择可能产生错误的值。每个值都是一个测试用例。
This technique can produce **both normal and error Test Cases**. The values selected are those that are likely to expose faults in the code, they are not necessarily illegal values. / 这种技术可以产生正常和错误的测试用例。选择的值是那些可能暴露代码中故障的值，它们不一定是非法值。
Input Test Data is selected, based on Test Cases which are **not yet covered**. As with the other test techniques, error cases should be executed **individually**. / 根据尚未涵盖的测试用例选择输入测试数据。与其他测试技术一样，错误用例应单独执行。
With experienced testers, this can be a very **effective complement** to other testing techniques. / 有经验的测试人员，这可以成为其他测试技术的非常有效的补充。
It depends on **how well the testers know the types of mistakes** that the developers are likely to make, or mistakes that have a high impact on the final product. / 这取决于测试人员对开发人员可能犯的错误类型或对最终产品影响大的错误的了解程度。

#### 执行步骤
**Scenario Testing Goal**
- Simulate the user to complete the operation of normal functions and core business logic to **verify the correctness of software functions**;
- Simulate the main errors in user operation to **verify the abnormal error handling ability of software**.

场景测试目标
- 模拟用户完成正常功能和核心业务逻辑的操作，验证软件功能的正确性；
- 模拟用户运营中的主要错误，验证软件的异常错误处理能力。

Alternative flows, like the program execution paths, will cause the scenario explosion.
Typical scenarios need to be selected for testing.
(1) One and only one scenario contains the basic flow;
(2) The minimum number of scenarios: the total of basic flows and alternative flows;
(3) For an alternative flow: at least one scenario covering it, which try to avoid covering other alternative flows

替代流程，如程序执行路径，将导致场景爆炸。

需要选择典型场景进行测试。
（1）有且仅有一个场景包含基本流程；
（2）最小场景数：基础流、备选流合计；
（3）对于备选流：至少覆盖一个场景，尽量避免覆盖其他备选流

  
1. According to the specification, **describe the basic flow and alternative flow** of the software under test.
根据规范，描述被测软件的基本流程和备选流程。
2. **Construct different scenarios** to meet the requirements of test completeness and no redundancy.
构造不同的场景，满足测试完备性和无冗余的要求。
3. **Design corresponding test cases** for each scenario.
为每个场景设计相应的测试用例。
4. Re-examine all generated test cases and remove redundant test cases. After the test cases are determined, **the test data values are determined** for each test case.
重新检查所有生成的测试用例，去除冗余的测试用例。测试用例确定后，为每个测试用例确定测试数据值。
